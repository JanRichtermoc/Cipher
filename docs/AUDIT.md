# Cipher — security audit ledger

Every known weakness, accepted trade-off, and unfinished control, in one place.

This file exists because `Vendor/libsignal/DECISIONS.md` requires it, and because a security
argument that lives only in code comments cannot be reviewed as a whole. **An item is only
removed from here when the control that closes it exists and is tested.** Downgrading an item
to "probably fine" is not closing it.

Status legend: **OPEN** — unmitigated · **ACCEPTED** — understood, deliberate, compensated ·
**CLOSED** — a tested control exists.

**Columns.** *Adversary* names the section of [`THREAT_MODEL.md`](THREAT_MODEL.md) §1 the finding
matters to — a finding with no adversary is a bug, not a security finding. *Fix in* is the stable
step id in [`CLAUDE_IMPLEMENTATION_PLAN.md`](CLAUDE_IMPLEMENTATION_PLAN.md) that closes it, so the
ledger and the roadmap cannot drift apart.

**Ids are permanent and are cited from code, scripts and the other docs.** Never renumber a live
id; if two items ever collide, the more-cited one keeps the number and every citation of the other
is updated in the same commit.

**A CLOSED entry states the invariant and the guard that enforces it**, not the story of how it
was found. What matters going forward is what must stay true and what would notice if it stopped
being true. Compressed 2026-07-29; the narratives are recoverable from git history.

Last reviewed: 2026-08-06, after the first P5.S13 staging run found and closed 5.32 — the relay
refused every prekey publication a real client could send. Before it, P5.S12 closed 2.5 with a
real safety number; before that, the
staging deployment that closed 5.29 on the live box and the
backend and infrastructure remediation that closed 5.28; before them, the P5 verification and build
remediation that closed 6.14 and 6.13, the supply-chain remediation that closed 1.14 and 1.3, the
backend remediation that closed 5.27, and the transport remediation that closed 5.26.

## 0. Recurring failure modes

Five classes have each produced multiple findings. Stated once here as rules, because they were
first recorded as facts about one command and recurred anyway.

**R1 — Never put an infinite or long producer upstream of a consumer that exits early.**
(1.9, 1.10.) `head -c`, `grep -q` and `grep -m` all close the pipe; `xcodebuild` raises
`NSFileHandleOperationException` and GNU `tr` reports `write error: Broken pipe`, so under
`set -o pipefail` a *succeeding* pipeline fails the build. BSD and BusyBox variants die quietly,
so it works on macOS and alpine and fails on `ubuntu-24.04` — it passes locally and breaks in CI.
Buffer into a variable, or make the finite side the producer. **Live trap:** `verify-all.sh`'s
`xcodebuild | grep | sort -u | grep -q` pipelines are safe only because `sort -u` cannot emit
until it has read all input. Removing the `sort` in a cleanup reintroduces 1.9.

**R2 — A gate that has never been made to fail is not a gate.** (1.9, 5.12, 6.7, 6.8, 5.16, 5.28.)
Four ways it has actually gone wrong here: the check scanned prose that *describes* the control
rather than the control (comments naming the very strings being forbidden — strip comments
first); the check trusted an exit code that carries no meaning (`docker compose port` exits 0
saying `invalid IP:0`); the check aborted before running and its silence was read as an
accusation; and the check was run with an instrument that cannot express the negative (macOS
`openssl` is LibreSSL and cannot drive a `-tls1_3` probe, so it reported an impossible
"1.2 refused / 1.3 refused"). Every gate in this repo is negative-tested by reintroducing the
defect. A gate that cries wolf is as dangerous as one that never fires — it gets deleted.

**R3 — `#if DEBUG` fences code, not resources.** (5.10, 5.11.) `Localizable.xcstrings` compiles
into the bundle regardless, and Xcode emits every translated `stringUnit` even for keys it drops
from `en.lproj`. Any audit of "what ships" must read the whole `.app`, not the Mach-O.

**R4 — A control removed from the source survives in its translations.** (5.4, 5.10, 5.13, 5.14.)
Deleting an English string leaves its `cs` rendering in the catalog, and a guard list written in
English silently exempts every other language ("passcode" → "kód zařízení").
`Scripts/verify-localization.py` searches every language and carries a `--self-test` that
reintroduces each defect before its own verdict is believed.

**R5 — A self-test can be wrong in the same way the check is.** (6.14, 6.16, 5.29, 1.14.)
Every gate here carries a self-test, and writing them surfaced four distinct ways the
self-test itself passes without proving anything. **Do not derive the cases from the data
under test:** the simulator-fault self-test looped over the pattern list, so deleting a
pattern deleted its own case and the suite stayed green — the exact defect 6.14 records,
reproduced inside its fix. Observed inputs go in as literals. **`set -e` turns a bare
call into a silent exit:** `chain_is_verified "$x"` on its own line aborts the script when
it returns non-zero, which made a pin self-test exit 1 with no output *and* would have
turned "this certificate failed validation" into a silent failure at the live call site.
Use `|| rc=$?`. **A subshell cannot report a failure flag:** running checks inside
`$(...)` to capture their output left `FAILED` in the child, so five negative cases read
as accepted. Redirect to a file instead. **And a wait is not free of the harness:** test
ceilings must stay below whatever escape hatch the fixture uses, or a wait that outlives
it stops observing the property and starts observing the timeout — silently a different
test (6.16).

A self-test that has never been made to fail is worth exactly as much as the gate it is
supposed to validate. Reintroduce the defect in the *real* file, not only in a fixture:
that is what caught the two cases above where the fixture was fine and the wiring was not.

| 2.5 | **No user-facing safety-number screen. Closed 2026-08-06 (P5.S12).** Trust state existed, persisted, survived restart and blocked sending — but nothing rendered it, so 3.2's protection was half-delivered: a user was stopped from sending with no way to see *which* key they were being asked to accept, which is the difference between a key rotation and an attack. `CryptoEngine.safetyNumber` derives the sixty digits through libsignal's `NumericFingerprintGenerator` over both identity keys and both ACIs; iterations and version are format constants, not settings, because two builds disagreeing on either would produce different numbers for the same pair and users would read that as an attack. **Verification is stored bound to the exact key** — a `verifiedFlag` bit inside `PeerIdentityRecord` rather than a separate table — so there is no record of "this peer is verified" that could outlive the key it was asserted about, and `saveIdentity` writes a changed key with the bit clear. That makes "invalidate on identity change" a property of the format rather than of someone remembering to clear it. **Accepting and verifying are kept separate**, which is 5.4's lesson applied: accepting a changed key unblocks sending, verifying asserts the digits were compared with the person, and a single control for both would make the badge mean only that a warning was dismissed. The screen says so in its own copy. Both write paths name the key they apply to, so a change arriving between the screen being drawn and the tap is refused rather than silently approved. The record format anticipated this exactly: its `knownFlags` comment already named "a future build — one that had, say, added a *verified* bit" as the case it refuses rather than misreads, so a build predating this reads a verified peer as unreadable instead of unverified. That direction is deliberate — a discarded verification looks conservative and is not, because it silently retracts a claim the user made after comparing digits. The cost is a downgrade path that loses peer identity records, bounded by `saveIdentity` treating an unreadable record as first contact. `VerificationDisplay.isAvailable` flips to true and the badge is backed by a real claim for the first time; the gate itself stays, so turning it off again remains one edit. The localization denylist entry forbidding "Safety Number" is retired with its reasoning, because the claim it existed to stop is now true — and what replaces it is `SafetyNumberTests`, since a denylist can only stop a retired claim returning, never a new invention (5.4's recorded residual). Guards: nine `SafetyNumberTests`, including the plan's two "Done when" halves proved against **two real engines** rather than an engine and a fixture — `testTwoEnginesAgreeOnTheSafetyNumber` and `testASubstitutedIdentityChangesTheSafetyNumber`. Negative-tested by reintroducing each defect in the real source: carrying the verified bit across a key change failed `testVerificationIsClearedWhenTheIdentityChanges` by name with "a verified badge survived an identity change"; dropping the exact-key check failed `testVerifyingRefusesAStaleKey`; and making acceptance confer verification failed `testAcceptingAChangedKeyDoesNotVerifyIt`. **Two residuals, stated rather than implied.** (a) QR scanning is deliberately not built: it needs a camera permission this app has never had and a new attacker-facing input path, and a QR *render* with no scanner would be an inert affordance of exactly the kind 5.4, 5.21 and 5.30 removed.
