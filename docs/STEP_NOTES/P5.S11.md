## 1. What already exists

Confidentiality is **already achieved**. AUDIT 4.3 says so in as many words: *"The residual is
performance and query shape, not confidentiality."* This step must therefore add queryability
**without regressing what is sealed today**. That framing decides most of what follows.

| File | What it contributes |
|---|---|
| `Cipher/Messaging/ConversationArchive.swift` | The interface that survives. `StoredConversation` / `StoredMessage`, ordinals, the crash ordering, `SerialGate`. Storage format is what changes. |
| `CipherCrypto/Sources/Store/SealedAppStore.swift` | Today's backing: `storeSealed` / `loadSealed` / `removeSealed`, bytes in and bytes out. Its header states the boundary this step must not cross. |
| `CipherCrypto/Sources/Store/EncryptedFileRecordStore.swift` | The sealing pattern to copy: AES-GCM, AAD = `version ‖ kind ‖ 0x00 ‖ key`, size ceiling checked before reading, `.atomic` writes, backup exclusion, `completeUntilFirstUserAuthentication`. |
| `CipherCrypto/Sources/Store/RecordStore.swift` | `RecordKind.appData`, and the deliberate absence of key enumeration. |
| `Cipher/App/AppSession.swift:44-52, 109-111, 186-194` | The three `UserDefaults` profile fields, and the existing precedent for removing a retired key on launch (`cipher.isAuthenticated`, `cipher.screenshotWarning`). |

## 2. Four constraints that decide the design

1. **No new dependency** (root `CLAUDE.md`, “Locked boundaries,” and `THREAT_MODEL.md` §4.1 —
   *one* dependency, not “prefer fewer”). So:
   SQLite through the SDK's own module. **Not SQLCipher** (a dependency) and **not SwiftData**,
   whose storage format is opaque — "no plaintext at rest" would become a claim about Apple's
   internals rather than something a test can read off the bytes.
2. **One Keychain item stays the cryptographic erase for everything.**
   `SealedAppStore.swift:20` is explicit. So the database is sealed under a subkey **derived from
   the existing record encryption key**, never a second Keychain item — otherwise "delete
   everything" deletes half of it.
3. **The crypto module must not learn what a conversation is.**
   `SealedAppStore.swift:34-38` states this deliberately. So the new store is **generic**:
   namespace, an opaque group tag, an ordinal, a sealed blob. The app maps conversations onto it.
4. **Everything stays on `@CryptoActor`**, in the same container, excluded from backup, at the same
   file-protection class — including SQLite's sibling files, which is where this can go wrong
   quietly.

## 3. The design

A generic sealed, queryable store in `CipherCrypto/Sources/Store/`:

```sql
CREATE TABLE sealed_record (
  namespace TEXT NOT NULL,   -- 'conv', 'msg', 'profile' — opaque here; in the source anyway
  group_tag BLOB NOT NULL,   -- blind index (see below); names nobody
  ordinal   INTEGER NOT NULL,-- caller's ordering key; 0 for a singleton
  sealed    BLOB NOT NULL,   -- AES-GCM, AAD binds namespace ‖ group_tag ‖ ordinal
  PRIMARY KEY (namespace, group_tag, ordinal)
) WITHOUT ROWID;
```

- **Blind-indexed group tag.** A peer UUID must not sit in a plaintext column. Today's filenames are
  `base64url(SHA-256(kind ‖ 0x00 ‖ key))`, so the container names no correspondent, and a plaintext
  peer column would be a straight regression — the social graph is the thing this design most
  refuses to hand anyone. The tag is `HMAC-SHA256(index-subkey, peer-bytes)` truncated to 16 bytes:
  equality lookups still work, ordering within a conversation still works, and the file names nobody.
- **Two subkeys, both HKDF-SHA256 from the record key**, with distinct `info` strings — one for
  sealing, one for the index. Distinct so bytes can never be meaningful in the other role.
- **AAD carries the slot**, exactly as the file store does, so a row copied between slots fails to
  open instead of being believed in its new position.
- **Transactions.** `append` (write the message, advance the counter) becomes one transaction. This
  is strictly better than today's write-ordering argument, and it is why `SerialGate` **stays**:
  AUDIT 4.10 is CLOSED with the gate as its named guard, and removing it would reopen 4.10. The
  transaction is defence in depth, not a replacement.
- **No unused columns.** An `expires_at_ms` column would make a disappearing-message sweep one
  `DELETE`, but disappearing messages are not this step, and a column nothing reads is the inert
  placeholder §5.3 forbids. What this step owes 4.3 is the *query shape*; the expiry predicate
  arrives with the feature.

### Migration, because silent data loss is not acceptable even pre-release

The old records **can** be enumerated without key enumeration: the archive's own index record lists
every peer, and each conversation record carries `firstOrdinal` / `nextOrdinal`. So a one-shot
migration reads exactly what `messages()` reads today, writes it into the database in one
transaction, deletes the old slots by key, and records that it ran. Nothing has shipped, but a dev
build losing its history silently is still the wrong behaviour, and this is testable.

**The defect this step found in itself.** With the wrong Keychain key, the *index* key differs too,
so `groupTag` produced a different tag, every lookup missed, and reads returned `nil`. Unreadable
state was degrading to "not found" — exactly what AUDIT 4.9 forbids, and something the file store
cannot do because its filenames are unkeyed. A device whose Keychain item was replaced would have
shown an empty conversation list and started writing beside the unreadable rows. Caught by
`testTheStoreIsUnreadableWithoutTheKeychainKey` before commit; fixed with a key-check row at a
constant tag, so the container refuses to open instead. Recorded in AUDIT 4.3.

## 8. Erasure remediation (2026-08-01)

The integrated P5 review reopened P5.S11 for the remaining AUDIT 4.13 failures. They are now
closed as one storage-boundary change:

1. **Cryptographic erase is first and resumable.** `destroyAllState` removes the Keychain service
   before unlinking ciphertext. Once erasure starts, the engine refuses all non-erasure work. A
   missing key beside any non-empty crypto root is an error, never permission to create a
   replacement key — including when a downgraded build does not recognize a newer artifact;
   the persisted `.destroying` account gate can finish deleting the exact crypto root without
   opening it.
2. **Logical deletion removes recoverable SQLite residue.** Every connection verifies
   `secure_delete=ON`. Deletes and replacements receive a `TRUNCATE` checkpoint, including shared
   transactions. A sealed, marker-after-success migration runs `VACUUM` once to scrub free pages
   written by older builds. A post-commit checkpoint failure is retried before later work and on
   open; the inbound path never mistakes that failure for a rolled-back ratchet.
3. **Profile persistence preserves the newest account-scoped value.** One coalescing writer owns
   the latest snapshot. Its captured archive and account generation prevent a cancelled old write
   from resuming against a later account, and destructive account cleanup detaches the queue.
4. **Legacy cleanup is durable.** Committed protocol rows and tombstones retain the original legacy
   key. Every database open retries leftover file removal, even when an earlier post-commit unlink
   failed after the migration marker became durable.

## 9. Storage quota (2026-08-04) — AUDIT 4.14, and the end of P5.S11

The last open item. Anyone who can fetch this account's published prekey bundle can establish a
session, so inbound volume is unauthenticated growth — the same shape as 3.1's witness FIFO.
Individual records were already bounded (32 KiB payload, 1 MiB row); nothing bounded their
*number*.

### Three bounds, because none implies the others

| Bound | Value | Why it cannot be dropped |
|---|---|---|
| Conversations | 256 | Without it, the byte quota is defeated by spreading one message across very many conversations: eviction reclaims by trimming long conversations, and a container of short ones has nothing to give. |
| Messages per conversation | 5 000 | The cheap, exact bound. Needs no counting — `nextOrdinal − firstOrdinal` is already known. |
| Logical container size | 192 MiB, evicting to 160 MiB | The only one that bounds *disk*. The other two leave 256 × 5 000 × 32 KiB of headroom. |

**`page_count` is the wrong measure and quietly so.** SQLite never returns freed pages to the
filesystem — it moves them to a freelist and reuses them — so the file does not shrink on delete,
and a quota built on `page_count` would trip once and then evict on every append forever, against
a figure that never moves. The measure is `(page_count − freelist_count) × page_size`. Both are
header reads, so it is cheap enough for the receive path, and both reflect an **open**
transaction — which eviction depends on, because it must see the space it just freed to know when
to stop. Asserted by `testFreedSpaceIsVisibleToTheQuotaInsideTheSameTransaction`, not assumed
from the documentation.

### The three properties that make it a control rather than a liability

1. **Eviction takes from the largest conversation.** A flooding peer therefore trims its own
   history first. Picking the oldest, the least recently active, or simply the first found would
   have turned filling the store into a way to delete *somebody else's* messages remotely —
   strictly worse than the disk exhaustion it was added to stop.
2. **Nothing is trimmed below a floor of 8**, so eviction cannot empty a conversation and — the
   case that matters — cannot delete the message whose own append triggered it.
3. **All of it runs inside the append's transaction.** Either the message and the trim commit
   together or neither does, and the receive path acknowledges only on that commit. So
   "acknowledge only what is durable" is unchanged.

### Why `quotaExceeded` is acknowledged

A first message from a new peer at the conversation cap joins `blocked` and `unsupportedPayload`
in the acknowledgeable family, not the thrown-storage-failure one. The ratchet advanced and
committed inside the decrypt transaction, so the envelope can never decrypt again — withholding
the acknowledgement would not preserve it. It would leave the relay serving the same
undecryptable bytes every cycle, and `receiveExclusively` stops taking messages behind a storage
failure, so a device at its cap would stop receiving from **everyone**. Existing conversations
are never evicted to make room, so the loss is bounded to correspondents this device has never
spoken to.

### Left undone, deliberately

- **AUDIT 4.15**, the residual this bound costs, recorded rather than hidden: an attacker holding
  many identities can occupy conversation slots, after which a genuine new contact's first
  message is dropped — logged, with no UI. And an attacker who spreads across slots rather than
  flooding one can make a legitimate conversation the largest and cost it its oldest messages.
  Both beat the alternatives, and each attacker identity costs a prekey. The user-facing half
  lands with the P5.S13 UI pass.
- **`append` still creates a conversation record uncapped** if called for an unknown peer. Not
  reachable adversarially — `sendExclusively` goes through `startConversation` →
  `ensureConversation`, which is capped, and the inbound path has its own check — so this is a
  test-only path today. Noted so a future caller of `append` knows the cap is not there.
- **Disappearing messages are still not implemented.** Retention here is a quota, not an expiry
  policy; the expiry predicate still needs a column, and a column nothing reads is the inert
  placeholder §5.3 forbids.
