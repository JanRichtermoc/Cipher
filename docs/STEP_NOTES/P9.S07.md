## Method

Each item is executed against the substrate where the property actually lives, and the substrate is
named — a control that lives in the client is proved in the client, and a control that lives in the
relay is proved against a real relay, never a mock. Three substrates appear:

- **client** — the app/crypto XCTest suites, run this session through `./Scripts/verify-all.sh`:
  **250** `CipherCrypto` cases and **126** `Cipher` cases, 0 failures, gates 1–18 green.
- **relay (containerised)** — `./Scripts/verify-relay-integration.sh`: the real relay binary against a
  real Postgres and a real Redis inside the compose network. **148 tests, 30 required by name, exit 0.**
- **relay (live staging)** — probes against the deployed box, `relay.mgchatman.app`. At probe time the
  deployed revision was `6e6bbf2` and `git rev-list --count HEAD..origin/main -- server/` was **0**, so
  the live binary is byte-for-byte the one the containerised suite exercises; the live delta is nginx,
  TLS, the real network, and the real datastores — which is exactly the layer AUDIT 5.32 and 5.33 were
  found in while the tests were green.

**Secret hygiene.** The live account flow mints a throwaway invite and redeems it. The invite code and
the session token are secrets (root `CLAUDE.md`); the whole flow therefore runs inside one remote
shell and prints only HTTP status codes, row counts and booleans. No code, token, database password,
or account identifier was returned to the workstation. Database reads referenced the container's own
`$POSTGRES_PASSWORD` inside `docker exec`, so the value never left the container. The throwaway
accounts were emptied and their sessions revoked; the account rows are left to the abandonment sweep,
itself a tested control (`TestAbandonedAccountsAreDeleted`).

## The nine items

| # | Item | Substrate(s) | Result |
|---|------|--------------|--------|
| 1 | `UserDefaults` bypass | client | Held. Writing `UserDefaults` cannot authenticate. |
| 2 | MITM with the wrong pin | client + live | Held. Served leaf matches the shipped pin; a mismatched/empty pin set is refused; TLS 1.3-only. |
| 3 | Relay rewriting `Envelope.sender` | client + relay | Held. Attribution follows the decrypting session; the relay stores/serves opaque bytes and never parses the envelope. |
| 4 | Relay replaying a captured prekey message | client + relay + live | Held. libsignal rejects a replayed prekey message; the relay does not dedupe, fetch is non-destructive, ack is idempotent. |
| 5 | Prekey-pool exhaustion | relay + live | Held. Fetch throttle fired at the 11th request on the deployed relay; the pool has a per-account ceiling. |
| 6 | Invite brute force | relay + live | Held. Redeem throttled to 5/hour end-to-end through nginx; unknown codes are an identical 401 with no oracle. |
| 7 | Base-key witness flooding | client | Held. The witness set is FIFO-bounded; the oldest is evicted, not retained forever. |
| 8 | Post-first-unlock device extraction | client | ACCEPTED residual (AUDIT 2.1). Crypto records are `AfterFirstUnlockThisDeviceOnly`, non-synchronizable — extractable after first unlock by design; the session token is the stricter `WhenUnlockedThisDeviceOnly`. |
| 9 | Delivered messages are actually gone from the server | relay + live | Held. Ack deletes the row; a live `SELECT count(*)` went 1 → 0; no archive table exists. |

### Item-by-item detail

**1 — `UserDefaults` bypass (client).** `isAuthenticated` derives from a Keychain-backed
`SessionCredential`, not a `UserDefaults` bool; `destination` cannot reach `.main` without an active,
unexpired credential. Guards: `SessionCredentialTests.testWritingUserDefaultsCannotAuthenticate`,
`testCredentialPresenceIsTheAuthenticationState`, `testPendingRegistrationSurvivesRelaunchWithoutExposingMain`.
The retired `cipher.isAuthenticated` key is actively deleted on launch
(`testTheRetiredUserDefaultsKeyIsCleared`).

**2 — MITM / wrong pin (client + live).** Client: `CertificatePinnerTests` proves the shipped pin set
contains the live leaf's SPKI, that a mismatched set is refused (`mismatchedPinIsRefused`) and that an
empty set refuses rather than permits (`emptyPinSetRefuses`). Live: `Scripts/verify-pins.sh
relay.mgchatman.app --partial` reported *served leaf matches a shipped pin*, *certbot reuse_key =
True*, and *RelayEndpoint.swift pins exactly the values in BACKEND.md §9.1*; a direct `openssl
s_client` showed TLS 1.2 refused (alert 70) and TLS 1.3 with `Verify return code: 0`. The only skipped
sub-check is the emergency backup-key pin (`PIN_BACKUP_KEY_FILE` unset — the known AUDIT 6.14 gap).

**3 — Relay rewriting `Envelope.sender` (client + relay).** The client attributes messages to the
session that authenticated the ciphertext, never to the routing field
(`MessagingTests`/`SealedSenderTests`; sealed sender writes seventeen zero bytes where the sender
used to be). The relay never reads the field: `TestTheRelayDoesNotInspectTheEnvelope` and, live, the
self-send in item 9 stored and returned the envelope bytes verbatim. The standing residual that a
*first* message's label rests on a self-issued certificate is AUDIT 3.8, out of scope here.

**4 — Replayed prekey message (client + relay + live).** The client rejects a replayed
`PreKeySignalMessage` at the libsignal layer; the relay's own replay behaviour is pinned by
`adversarial_integration_test.go:TestReplay`. Live, the relay layer was shown non-amplifying: a plain
re-fetch returned `200` without deleting or duplicating, ack removed the row, and a second ack of the
same id returned `200` (idempotent, no resurrection and no oracle).

**5 — Prekey-pool exhaustion (relay + live).** Two ceilings. Drain rate: the fetch route is throttled
(`fetchBurstLimit` 10/hour, `fetchDailyLimit` 30/day, keyed by caller) — live, twelve sequential
`GET /v1/keys/{aci}` returned `404 404 404 404 404 404 404 404 404 404 429 429`, the throttle firing
exactly after ten. Pool size: a per-account cumulative ceiling clips rather than refuses
(`keys_integration_test.go:TestAPreKeyPoolStopsGrowingAtItsCeiling`,
`TestAFullPoolStillRotatesTheLongLivedKeys`). Drain is bounded and observable; both were built by the
audit campaign (5.40) and by P4.S06.

**6 — Invite brute force (relay + live).** Eight rapid `POST /v1/invite/redeem` with well-formed but
unknown codes returned `401` for the first attempts (identical response body hash regardless of the
differing guess — no oracle), then `429` with `Retry-After: 699` (~one token per 12 min = 5/hour). The
bucket had one prior token spent by an aborted probe invocation, so four `401`s appeared here; 4+1 = 5
= `redeemLimit.Capacity`. Bodies were the generic `{"error":"Too Many Requests"}` / `Unauthorized`
with no path or code echoed. This exercised nginx + `X-Real-IP` + the Redis limiter end-to-end.
Guards: `invite_integration_test.go:TestRedeemEndpointThrottlesBruteForce`,
`TestRedeemEndpointResponseIsIdenticalForUnknownAndUsed`, `TestRedeemRateLimitsBeforeParsing`.

**7 — Base-key witness flooding (client).** The base-key witness set is FIFO-bounded at
`CipherProtocolStore.baseKeyWitnessCapacity`;
`ProtocolStoreTests.testBaseKeyWitnessEvictsOldestAtCapacity` fills past capacity and proves the
oldest entry is evicted rather than retained without bound, and
`testBaseKeyWitnessSurvivesAStoreRestart` proves it is durable. This is the mechanism behind the
ACCEPTED AUDIT 3.1: replay is bounded, not prevented, and rotation ends the window.

**8 — Post-first-unlock device extraction (client, ACCEPTED residual).** Crypto records are stored
`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly` with `kSecAttrSynchronizable = false`
(`SecretStorage.swift`; asserted by `RecordStoreTests`), so an attacker who images the device after
its first unlock *can* read them — this is the deliberate trade-off in AUDIT 2.1 and locked decision
§0.2.6, the price of wake-only push decrypting in the app's own process. The session token is held to
the stricter `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`. No jailbreak/debugger hardening exists
and is not claimed (AUDIT 6.4, P10.S04). Nothing here is a new finding.

**9 — Delivered messages are gone (relay + live).** Live self-send round-trip on the deployed relay:
queue `0` before send, `202` on send, queue `1` after, a read-only `SELECT count(*) FROM messages
WHERE recipient_aci = …` returning **1**; then ack `acknowledged: 1`, queue `0`, and the same
`SELECT` returning **0** — the row is deleted, not hidden. `TestThereIsNoArchiveTable` proves no
second table retains it, `TestAcknowledgementDeletesTheRow` and `TestFetchingDoesNotDelete` pin the
delete/non-delete split, and `TestSweepRemovesExpiredMessages` covers the unfetched path.

## Residuals recorded, not closed here

- **AUDIT 3.9** (OPEN): a *live* relay still learns the sender from the bearer token on `POST
  /v1/messages`. The probes did not and cannot change this — closing it needs an unauthenticated
  delivery path, which is unscheduled. Its status is the subject of the new P9.S09.
- **AUDIT 2.1 / §0.2.6** (ACCEPTED): item 8's post-first-unlock extractability, as above.
- **AUDIT 6.14** (known): the emergency backup-key pin sub-check was skipped because its key file is
  not present on the workstation; every other pin sub-check ran and passed.
- **AUDIT 6.4** (OPEN): no jailbreak/debugger/screenshot hardening — deferred to P10.S04, not a
  control and not marketed as one.

## Not done live, and why

The external pen-test engagement is **P9.S08** (human-owned) and is not this step. Sealed-sender
"the relay learns nobody" was verified against the frame bytes and the schema, not by reading real
traffic on the box, for the reason the P7 exit criteria already record: confirming it by querying the
live database means reading real private mail, which the root contract forbids. The client-side items
(1, 7, 8) are not live-relay items; their substrate is the client, so the XCTest suites are the
correct place they were executed, and no live analogue exists.
