# P5.S09 — Account-bound registration and session lifecycle

**Plan row:** redeem an invite against the relay, store the returned session in the
`WhenUnlockedThisDeviceOnly` Keychain item, and let only a real server-issued credential pass the
authentication gate.

> **Done when:** Real server-issued, account-bound token gates access; interrupted registration and
> cleanup recover; prior-account history cannot cross sign-in.

This remediation closes AUDIT 5.25 and the cross-account portion of 4.13.

## Invariants

1. Invite consumption, account insertion, and the first session-token hash commit or roll back in
   one PostgreSQL transaction. The plaintext token exists only in process memory and the response.
2. The Keychain value binds token, ACI, issue time, server expiry, origin, and lifecycle phase.
   Unknown versions and malformed values never authenticate.
3. `.registering`, `.profileSetup`, and `.destroying` are persisted recovery gates. Only `.active`
   and unexpired can render main or authorize messaging.
4. Registration adopts exactly the credential ACI before publishing keys. Every send and receive
   rechecks that the current credential ACI equals the crypto engine's local address.
5. Rotation begins seven days before expiry, is single-flight, and is never transport-retried: the
   server consumes the old token. A replacement must preserve ACI and extend a bounded expiry.
6. Sign-out, local expiry, relay rejection, and an unreadable legacy credential keep another invite
   unreachable until protocol state, sealed rows, and all in-memory account models are erased.

## Implementation

| Area | Change |
|---|---|
| Relay redemption | `store.RedeemInvite` accepts `InitialSession`; the handler generates the token first and commits its hash with the account and invite deletion. |
| Credential | Binary Keychain format v2 adds ACI, issue/expiry timestamps, and phase; server tokens must be canonical 32-byte unpadded base64url values. Updates replace the item atomically. |
| Registration | Redemption persists `.registering` before crypto work. The root recovery screen resumes address adoption/key publication and then persists `.profileSetup`. Profile setup saves the sealed row before `.active`. |
| Messaging | Registration reads the pending credential instead of a caller-supplied ACI. Active send/receive read the Keychain on every operation and reject account mismatch or local expiry. |
| Rotation | `SessionLifecycle.rotate` calls the relay once. `AppSession` serializes foreground attempts, prevents an overlapping sync from using the old token, and rejects a cross-account or non-extending replacement. |
| Cleanup | `.destroying` is stored before erasure. `ConversationStore.destroyAccountState` destroys the crypto container and drops engine, repository, conversations, contacts, messages, ordinals, and local ACI before the session item is cleared. |
| Foreground expiry | A root task wakes at the stored deadline and persists `.destroying`; scene activation also enforces expiry. A visible cleanup pass re-reads a temporarily unavailable `WhenUnlocked` item before erasing it. |

## Residuals

- A response lost **after** a committed invite redemption still loses the only plaintext token and
  requires another invite/new account. Retrying a single-use redemption cannot recover that token
  and risks creating another stranded account; the client therefore sends it once. There is no
  password, email, or recovery secret by design (`THREAT_MODEL.md` §3.4).
- A lost rotation response invalidates the stored old token. Its next 401 enters destructive
  cleanup; retaining both tokens would turn rotation into issuance and preserve a stolen token.
- AUDIT 4.13 remained OPEN here for P5.S11 remediation: cryptographic-erasure crash ordering,
  SQLite secure deletion/WAL residue, ordered profile writes, and retryable legacy cleanup. It was
  closed by the 2026-08-01 P5.S11 erasure remediation.

No staging deployment is part of this source step. The relay change deploys only after review and
merge through the normal runbook.
