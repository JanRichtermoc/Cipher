# P9.S04 — Monitoring and alerts that carry no metadata

**Plan row:** metrics and alerts **without message content** — cert expiry, disk, auth anomalies,
error rates.

> **Done when:** alerts fire in a drill. **Do not:** log message metadata.

Staging half only, under the P9 precondition amendment of 2026-08-11. No finding changed status. The
step found and fixed **three defects in its own work by running it against the live box**, two of
which had already passed a self-test — recorded below rather than quietly corrected, because the
class matters more than the instances.

## Why this is a shell script on the host and not a `/metrics` endpoint

The obvious implementation is a Prometheus endpoint on the relay. It is the wrong one, for three
reasons that are the same reason:

1. `BACKEND.md` §7 ends with *"log volume is itself metadata: an error log that fires once per
   delivery is a delivery record"*, enforced by `TestNoLogLineIsEmittedPerDeliveredMessage`. A
   counter that increments once per delivery is that record under another name — and unlike a log
   line it is **retained and scrapeable**, so it is strictly worse. `messages.go` already records
   that the relay deliberately has nowhere to put a per-message counter.
2. A scrape endpoint is new authenticated surface on a service whose design is to have as little as
   possible.
3. Any hosted alerting target is a third party that learns when the relay is up — the class of leak
   §3.4 removes by collecting no identifiers and §4.1 by refusing SDKs.

So everything is derived from what the host already knows: container state, disk, the served
certificate, and **aggregate counts** over the access log nginx already writes and already rotates.
Nothing is retained that the log did not already hold, and nothing is sent anywhere.

**There is deliberately no notification channel.** Cipher has no operator email (ACME registration
uses none, on purpose) and will not take a third-party one. `monitor.sh` exits `0`/`1`/`2` for
ok/warn/critical, which is what a systemd timer, a shell loop, or an operator at a prompt can act on.
Installing the timer is left to the operator and to P9.S02, for the same reason P9.S05 left its cron
alone: a persistent unit on a live host is a deployment change, not a drill.

## What is checked

| Check | Source | Thresholds |
|---|---|---|
| Certificate expiry | `openssl s_client` against the live host | warn ≤21d, crit ≤7d |
| Disk | `df -P /` | warn ≥80%, crit ≥90% |
| Containers | `docker compose ps` | crit unless all healthy |
| Relay errors | count of `"level":"ERROR"` in the last hour | warn ≥1, crit ≥20 |
| Auth anomalies | count of `401` in the access log | warn ≥50, crit ≥500 |
| Throttling | counts of `429` and `4xx` | informational |

Every one is a **count or a status word**. The script never prints a log line, an address, a UUID, a
populated path, or a token: an alert outlives the log's 24h retention, so an excerpt in one is how a
retention policy gets repealed by an operational convenience.

## The three defects the drill found

**1. `grep -c` prints `0` *and* exits non-zero.** So `grep -c … || echo 0` emits **two** zeros, and
every integer comparison downstream dies with `integer expression expected`. The script ran green on
the workstation and produced this on the box:

```
/tmp/monitor.sh: line 92: [: 0
0: integer expression expected
```

Fixed with a `count_matching` helper, and **pinned by three self-test cases** — including that the
result is usable in an integer comparison, which is the property that actually broke.

**2. The access-log parser matched nothing, and reported a confident zero.** The first version
matched a JSON `"status":` shape. The real format is nginx's `minimal`
(`server/deploy/nginx/00-cipher-hardening.conf`):

```
$remote_addr $request_method $status $body_bytes_sent $request_time
```

— five space-separated fields, status in field 3. So the check scanned the file, matched nothing, and
printed **`401=0`**: a *"found nothing"* result with no evidence it had scanned anything. That is
**AUDIT R2** reproduced inside this step, and it is the one that would have survived to production,
because a monitor reporting zero failures looks exactly like a healthy service.

The fix is not only the right pattern. `summarise_access_log` now returns `parsed` alongside `total`,
and the caller **refuses to report a rate it could not compute**:

```
WARN  auth failures   log format not recognised — scanned 1 lines, parsed 0
```

Both are pinned: one self-test asserts the correct counts against a real `minimal`-format sample, and
another feeds it a JSON log and requires `parsed=0` rather than a confident answer.

**3. The access log is root-only.** `/var/log/cipher/` is `0700`, so the monitor must run as root —
which it will under a timer, but which meant the first live run degraded to a warning. Documented
rather than worked around; the script reports the unreadable path instead of skipping the check.

## Guards and negative tests

`monitor.sh --self-test` runs inside **verify-all gate 10** — the gate whose stated subject is
deployment configuration that must not log what the threat model forbids. Monitoring is exactly that:
deployment configuration that reads the access log.

| Defect reintroduced in the real file | Observed |
|---|---|
| Summariser echoes the log line (`$0`) into its output | *"the access-log summary miscounted (got '4 3 1 1 {…token:"AAAABBBBCCCC"}', want …)"* |
| Cert warn window collapsed to `-le 0` | *"a cert inside the warn window did not warn"* |
| `grep -c … \|\| echo 0` restored | *"counting an empty stream produced '0\n0', not a single 0"* |
| Restored | 24 cases pass |

**Stated accurately rather than overclaimed:** for the summary, the exact-equality assertion is the
primary guard and catches a leak first; the forbidden-substring sweep is a second, weaker net that
would still catch a leak if that assertion were ever loosened to a prefix match. The sweep is
load-bearing on the `note` emitter path, which has no equality assertion.

Positive controls throughout: a healthy cert, a healthy disk, a quiet relay and a correctly parsed
log must all read `ok`, and the emitter must still print the count it is given — so a check that
refused everything, or a redactor that printed nothing, could not pass for a working gate.

## The drill (staging, 2026-08-12)

Normal run, as root:

```
ok    cert expiry            75d remaining
ok    disk                   15% used
ok    containers             3/3 healthy
ok    relay errors           0 in the last hour
ok    auth failures          401=0 of 8 parsed requests
ok    throttling             429=0, 4xx=6
status: OK                                        exit 0
```

The `4xx=6` is real traffic — the 404s from P9.S07's prekey-fetch-flood probe — which is what says
the parser reads the live log rather than agreeing with itself.

**Drill A — every threshold forced to trip:**

```
CRIT  cert expiry            75d remaining
WARN  disk                   15% used
ok    containers             3/3 healthy
WARN  relay errors           0 in the last hour
status: CRITICAL                                  exit 2
```

Severity escalates to the worst check and the exit code carries it, which is what a timer acts on.

**Drill B — the R2 case, an unparseable log:**

```
WARN  auth failures   log format not recognised — scanned 1 lines, parsed 0
status: WARN                                      exit 1
```

The box was left clean: the script was removed, the checkout is clean, all three containers healthy.

## Deliberately not done

- **No timer installed.** A persistent systemd unit on a live host is a deployment change; the
  runbook documents the command and P9.S02 owns installation.
- **No notification channel.** No email, no third party. See above — this is a design position, not
  an omission, and the exit code is the interface.
- **No production monitoring.** P9.S02, blocked on the production VPS.
- **No per-account or per-address breakdown.** *Which* account or address produced a spike is exactly
  the correlation §7 refuses to make; the count is what an operator acts on.
