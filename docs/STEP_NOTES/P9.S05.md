# P9.S05 — Encrypted server backups and a restore drill

**Plan row:** encrypted server backups plus a restore drill; define RPO/RTO and account for message
ciphertext, public key material, metadata, and operational server secrets separately; backups inherit
the §3.1 retention rules.

> **Done when:** restore drill completed.

Run under the P9 precondition amendment of 2026-08-11, staging half only. **Opens and accepts AUDIT
4.16.** No other finding changed status.

## The problem this step actually had

A backup is the one operation that can repeal `BACKEND.md` §4 in silence. Nothing fails, no test goes
red — the deleted messages simply come back at restore time, with a delay equal to the retention
period. §4 already said so ("backups cover schema and account rows only"), and that sentence had no
mechanism under it: there was no backup tooling in the repository at all, so the rule was true only
because nothing implemented it. That is the same vacuous-pass shape as **5.36** and P7.S03's
`push_tokens` — a property that holds because the feature does not exist.

So the work is mostly *classification*, and the classification is the security content.

## What is backed up, and what each exclusion costs

| Table | In? | Reason |
|---|---|---|
| `accounts` | **Yes** | The `aci` is the address peers hold; the identity key is what their safety numbers are of. A new invite mints a *different* account, so this loss is unrecoverable. |
| `session_tokens` | **Yes** | The only credential path. `POST /v1/auth/rotate` needs the old token and redemption creates a new account, so a lost token hash means the owner must re-invite, take a different `aci`, and re-verify with every peer. Excluding it makes a restore worse than no restore. **Cost recorded as AUDIT 4.16.** |
| `messages` | No | §4: acknowledged means gone. Losing undelivered messages in a restore is the correct outcome. |
| `attachments` | No | As above, and the blobs are outside Postgres. |
| `invites` | No | A live account-creation credential; restoring one resurrects a consumed or expired credential. |
| `one_time_prekeys`, `kyber_prekeys` | No | Dispensed-then-deleted. A restored one-time prekey can be dispensed twice, which is exactly the forward secrecy **AUDIT 2.6** exists for. |
| `signed_prekeys` | No | Public and short-lived; the client republishes. |
| `push_tokens` | No | Metadata that outlives the message (P7.S03), rotated at 30 days, re-registered by the device. |

**The cost of excluding the prekey tables is bounded rather than argued.** `rotateKeysIfDue`
republishes on `MessageRepository.preKeyRotationInterval` — 48 hours — *regardless of any count*,
precisely because a pool drained between checks is not observable to the device. So a restored relay
is missing published prekeys for at most one rotation. Established sessions are untouched: the
ratchet is on the device, so existing conversations keep working through a restore. The visible
symptom is narrow — a **new** session with a restored account cannot start until its owner's next
rotation.

## Encryption: public-key, so the host cannot decrypt its own backups

`openssl cms -encrypt -aes-256-gcm` to a **recipient certificate**. The box holds only the public
half, so a seized host yields the archive and no way into it. A passphrase-symmetric scheme would
have put the key beside the ciphertext, which is the state `THREAT_MODEL.md` §1.1 already assumes the
adversary reaches. No new dependency: `openssl` is already on the host and in the image's toolchain.

Operational server secrets (`server/.env`, TLS private keys, the pin backup key) are deliberately
**not** in this archive. They are a separate custody domain — the root contract says so — and a
database backup is the wrong place for them. `INFRASTRUCTURE.md` § Backup objectives costs each one
on loss.

## RPO / RTO

Defined in `INFRASTRUCTURE.md` § Backup objectives: **RPO 24h**, **RTO ~1h to a serving relay**,
**RTO up to 48h for full new-session capability**. The RPO number is doing double duty and that is
deliberate — it is also the bound on AUDIT 4.16's revocation-resurrection window, so "back up more
often" and "shrink the 4.16 window" are the same lever.

## Guards

| Guard | What it refuses |
|---|---|
| `Scripts/verify-backup-scope.sh` (verify-all gate **11**) | A schema table classified as neither backed up nor excluded, a stale entry naming a table the schema does not have, an empty backup list, a schema the gate could not read, and any retention-critical table appearing in `BACKUP_TABLES`. |
| `server/deploy/backup.sh --self-test` (run by the gate) | A produced dump carrying a forbidden table, or missing a required one — checked against the **artifact's own** `COPY`/`INSERT` headers rather than the arguments meant to produce it, in both `COPY` and `--inserts` forms. |
| `backup.sh` structure | An allow-list (`--table=` per included table), never `--exclude-table`, so a table added by a future migration fails closed instead of shipping. And no `--recipient` refuses outright rather than writing plaintext. |

**The union check is the point.** The gate does not merely assert that `messages` is excluded; it
asserts `union(BACKUP_TABLES, EXCLUDED_TABLES)` is *exactly* the schema's table set. A table added by
a later migration therefore belongs to neither list and fails, rather than defaulting into whichever
answer the flags happen to produce.

### Negative tests

Reintroduced in the **real** files, not a fixture:

| Defect | Observed |
|---|---|
| `messages` added to the real `BACKUP_TABLES` | *"'messages' is in BACKUP_TABLES — a restore would reintroduce data BACKEND.md 4 deletes"* |
| `invites` removed from the policy entirely (simulating a new migration) | *"table(s) in the schema that the backup policy does not mention: invites."* |
| Restored | gate passes: *"all 9 schema tables are classified"* |

Both self-tests carry positive controls — a correctly scoped dump and a correct policy must **pass**,
or a check that rejects everything would look like a working gate.

## The drill (executed 2026-08-11, on the staging box)

Live database **read-only throughout**; the restore target was a scratch database created for the
drill and dropped at the end. Only counts and booleans left the box — no account identifiers, no key
material, no token hashes, no credentials. The drill used a throwaway keypair generated for it and
destroyed afterwards; the real procedure never puts the private half on the host.

OBSERVED, in order:

| Step | Result |
|---|---|
| Live before | accounts **5**, session_tokens **3**, messages **1** |
| Backup written | 4365 bytes, encrypted to the drill certificate; tables `accounts session_tokens` |
| Artifact is opaque | `file(1)` says `data`; **0** readable `COPY` strings in the ciphertext |
| Decrypt | succeeded; dump names exactly `accounts` and `session_tokens`; `messages` **0**, `attachments` **0** |
| Scratch restore | schema applied from the migrations (9 tables), then rows |
| **Restored counts** | accounts **5** (live 5), session_tokens **3** (live 3) |
| **Policy held through restore** | messages **0**, attachments **0**, invites **0**, one_time_prekeys **0**, push_tokens **0** |
| Integrity | identity-key lengths in range for all **5**; all **3** token rows join their account |
| Teardown | scratch database dropped (**0** remaining), drill artifacts removed |
| Live after | unchanged — accounts **5**, messages **1** |

The three counts that matter most are the zeros: they are the retention policy holding through a
**real** restore rather than in a comment.

## What this step deliberately did not do

- **No production backup.** P9.S02 owns that, and it stays blocked on the production VPS.
- **No scheduled cron on the box.** Installing a timer is a persistent change to a live host; the
  runbook documents the command and the cadence, and scheduling it is an operator decision that
  belongs with the production deploy rather than with a staging drill.
- **No restore over the live database.** The drill proves the mechanism; promoting a restore is a
  decision with a revoke-all step attached, and there was nothing to recover.
- **Nothing about the provider snapshot.** AUDIT 4.8 is unchanged and is re-argued at P9.S01.
